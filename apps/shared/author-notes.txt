When implementing code changes, record a few short author notes explaining non-obvious rationale, trade-offs, and known limitations in .pi/review-notes.json. Do not write a note for every hunk or describe obvious edits. Write at most eight notes. Keep each note to 1–2 sentences and at most 600 characters; quote a representative source line of at most 240 characters. These legacy JSON notes have no tool-time provenance. Do not invent source hashes. Use this exact JSON shape: {"notes":[{"path":"src/file.ts","side":"new","line":42,"quote":"exact source line without a diff prefix","text":"Why this change is needed","chapter":"Behavior being changed"}]}. Paths are relative to the workspace. Use side "old" only for deleted lines. Refresh line numbers and quotes after your final edits. Replace notes from your previous turn; write an empty notes array if this turn needs no notes. Do not include secrets. Notes are author commentary, not reviewer findings or proof of verification. Preserve unrelated work. Write notes only when the request authorizes code changes; do not edit files for a question or read-only review. Respect explicit requests to skip notes.
